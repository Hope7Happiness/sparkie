# Sparkie 三人分工

第一轮先用 **60–90 分钟验证风险、统一接口**，暂不急着搭建完整产品。以下时间为建议时间盒，A/B/C 由团队对应到具体成员。

| 人员 | 负责方向 | 第一步做什么 | 第一轮产出 |
| --- | --- | --- | --- |
| **A：会议与音频** | 入会、监听、语音播放 | 调查并实测会议接入方案，确认能否获取音频或字幕、能否播放声音、是否需要权限审批 | 选定一个 demo 平台，列出接入步骤与阻塞点 |
| **B：Agent 与任务系统** | 上下文、唤醒、前后台任务 | 画清“收到字幕 → 判断唤醒 → 快速回答或委派 → 返回结果”的流程，定义各层交换的数据 | 一张流程图，以及 transcript、任务状态、结果的接口约定 |
| **C：产品与 Demo** | 演示场景、纪要、结果页面 | 写一段三人会议的演示脚本，明确每句请求的预期行为，画出会后结果页草图 | Demo 脚本、纪要样例、验收清单 |

## 同步方式

1. **开始前 10 分钟**：三人确认最小目标——Sparkie 入会，被叫到后说“我在”。
2. **第一轮结束**：A 汇报平台可行性，B 根据接入能力确定接口，C 调整演示脚本；共同锁定唯一平台。
3. **进入实现后**：A 做真实音频闭环；B 用模拟字幕推进上下文与任务系统；C 用样例数据推进纪要与页面，三方并行。
4. **第一次联调**：优先打通“真实字幕输入 → 唤醒 → 固定语音输出”，再接模型和搜索。

## 人员匹配

- **A**：最熟悉 SDK、音频和环境排障的人。
- **B**：最熟悉异步后端与 LLM 的人。
- **C**：最擅长前端和表达的人。

**A 是早期关键路径，遇到接入阻塞时三人优先共同解决。** B、C 的第一轮文档工作可以独立推进，不必等待平台接入完成。

## 第一阶段边界

- 平台能力必须用官方资料和实际测试验证，尚未验证的项目明确标记。
- 只选一个会议平台、一个唤醒词；第一里程碑不依赖 LLM。
- 模拟字幕仅用于开发联调，不能作为真实入会或语音能力的验收证据。
- 暂不投入视频、主动插话、精准分人、复杂 UI、邮件与日历集成。
- 纪要中的负责人和截止时间只有在会议明确提及时才填写。
