# 协作方式：一人编码，两人测试反馈

团队当前决定：暂不按会议接入、Agent、产品页面分配固定开发负责人。先由 [@Hope7Happiness](https://github.com/Hope7Happiness) 与 Codex coding agent 一起搭建 primitive，形成可运行版本后，[@YIFANK](https://github.com/YIFANK) 和 [@bowenyu066](https://github.com/bowenyu066) 测试并反馈。之后三位成员轮换：每轮一人负责编码与集成，两人负责测试反馈。

目标是缩短“发现问题 → 复现 → 修复 → 复测”的循环，让测试发现的真实问题决定下一轮实现重点。

## 当前阶段

- `@YIFANK` 和 `@bowenyu066` 在版本可运行后测试；账号持有人仍可协助完成只能本人操作的配置，这不构成固定模块分工。
- 当前已有离线模拟、Deepgram STT/TTS 单服务实测和 Codex 单次上下文回答。真人麦克风输入、实际播放与回声控制、Zoom 入会尚未完成，不把现有模拟当作完整语音 primitive。

## 每轮怎么进行

1. **交付可测版本**：编码负责人提供 commit、启动命令、本轮要验证的行为与已知限制。每轮范围保持小，先围绕一个可观察的行为。
2. **两人测试**：一人按正常使用路径体验，另一人尝试边界和异常；测试视角每轮可互换，不形成新的固定职责。
3. **整理反馈**：先记录观察与复现证据，再讨论原因。区分 bug、需求变化和建议，避免把猜测直接当修复方案。
4. **修复并复测**：按是否阻塞核心演示排序。编码负责人复现后修复，原报告者用修复后的 commit 重跑同一场景；只有确认通过才关闭问题。
5. **轮换**：完成一轮交付与复测后，换下一位成员负责编码，其余两人测试。交接说明当前 commit、未解决问题、运行方式与环境要求。

每轮保持一个编码与集成负责人；两位测试者可以使用 agent 整理日志或构造测试输入。代码修复汇总到本轮负责人，避免多个未同步版本影响复现。

## 一条可用的反馈

```text
版本 / commit：
运行模式：simulate / hybrid / 真实本地音频 / Zoom
环境：设备、输入输出设备、语言（仅记录与问题相关的项）
复现步骤或原话：
预期行为：
实际行为：
出现次数 / 尝试次数：
证据：日志时间点、事件 ID，必要时附经同意的录音
影响：阻塞演示 / 影响体验 / 改进建议
```

不在反馈中附 API key、会议密码或无关私人会话。无法稳定复现的问题仍记录实际观察，标为待复现，不虚构原因。

## 第一轮真人测试重点

- 单独叫 “Sparkie” 和直接提问是否能唤醒；记录 10 次尝试。
- 讨论产品名字但没有请求时，是否误触发；记录 10 次普通对话。
- 不同成员、语速、距离和背景噪声下的行为。
- 回复是否能听清，是否听到自身声音后循环触发。
- 回复时继续说话、取消以及服务断开时的表现。
- 记录真实首段声音延迟，不用模拟进程计时代替。

未实现的能力标为“未实现”，不能作为已通过项目。第一里程碑仍是固定语音闭环；之后才增加上下文问答和后台任务。

技术栈保持 Zoom + Deepgram STT/TTS + Codex CLI / OpenAI API。配置见 [人工配置清单](manual-setup.md)，启动与当前能力见 [primitive](primitive.md)。原始 `prompt` 中的模块分工是历史建议，以本文件的最新协作方式为准。
